# RETENTION.md

이 문서는 "왜 이 앱이 계속 쓰일 것인가"를 다룬다. 독서모임 앱은 기능이 부족해서 죽는 경우보다, 쓰이는 습관이 만들어지지 않아서 죽는 경우가 많다. 이전에 이 모임에서 만든 앱도 그렇게 사장된 이력이 있다. 따라서 여기 나열된 장치들은 "있으면 좋은 기능"이 아니라 MVP 범위에 들어가야 하는 이유가 있는 항목들이다.

## 핵심 전제

**이 앱은 알림을 보낼 수 없다.** 이메일/푸시 인프라를 갖추지 않기로 했으므로(비용·복잡도 대비 참여자 5~8명 규모에 안 맞음), 사람이 대신 알려야 한다. 그래서 설계의 핵심은 "앱이 못 하는 일을 사람이 최소 노력으로 대신할 수 있게 만드는 것"이다 — 공유 문구 자동 생성이 이 앱에서 가장 사소해 보이지만 가장 중요한 기능인 이유다.

## 죽는 경로와 대응 장치

| 죽는 경로 | 대응 장치 | 반영 Phase |
|---|---|---|
| 링크가 단톡방 위로 사라짐 | 공유 문구 자동 생성 + 클립보드 복사(회차 상세 우상단 버튼, 모든 참여자 사용 가능) | Phase 4 |
| 열었는데 아무도 안 씀 → 재방문 안 함 | 참여 현황 표시("5명 중 3명 작성", 회차 목록과 상세 양쪽에) | Phase 4 |
| 관리자가 매달 논제 세팅에 지침 | 회차 템플릿에서 복제 생성, 이전 회차 구조 복제 | Phase 3 |
| 과거 자료는 구글 드라이브에 → 두 곳을 오감 | 붙여넣기 일괄 이관(미리보기 → 확인 2단계) | Phase 3 |
| 로그인이 매번 귀찮음 | 세션 90일 유지(DECISIONS.md 참고) | Phase 2 |
| 작성 단계가 많음 | 회차 상세에서 인라인 편집, 별도 페이지 이동 없음 | Phase 4 |

## 왜 각 장치가 그 형태인가

- **공유 문구는 관리자 전용이 아니다.** 관리자 한 명에게만 "알려야 할 책임"을 지우면, 그 사람이 바쁜 달에 그대로 묻힌다. 아무 참여자나 버튼 하나로 같은 문구를 만들 수 있게 하면 알림 책임이 분산된다.
- **참여 현황을 회차 목록에서부터 보여준다.** "내 답변 2/4 작성" 같은 개인화된 진행률은 로그인 직후 첫 화면에서 보여야 행동을 유발한다. 회차 상세까지 들어가야 보이면 그 전에 이탈한다.
- **템플릿과 이관 기능은 관리자 피로를 줄이기 위한 것이다.** 참여자용 기능이 아무리 좋아도, 매달 논제를 손으로 세팅하는 관리자가 지치면 애초에 회차가 열리지 않는다. "회차를 30초 안에 만들 수 있는가"(Phase 3 종료 조건)가 이 앱 생존의 선행 조건이다.
- **세션을 90일로 길게 둔 것은 사용 빈도(월 1회)에 맞춘 것이다.** 로그인 마찰은 작아 보이지만, 월 1회만 쓰는 서비스에서는 "로그인부터 다시 해야 하나"라는 생각 자체가 재방문을 늦추는 요인이 된다.
- **인라인 편집으로 페이지 이동을 없앤 것도 같은 이유다.** 작성 단계마다 새 페이지로 넘어가면 그때마다 "이걸 지금 끝까지 해야 하나"라는 이탈 지점이 생긴다.

## 이 문서와 다른 문서의 관계

- 각 대응 장치의 화면/동작 상세는 SPEC.md에 있다.
- "회차 템플릿", "붙여넣기 이관" 같은 기능이 왜 MVP에 들어갔는지의 근거가 바로 이 문서다 — SPEC.md에서 해당 기능을 수정할 때는 여기 적힌 이유가 여전히 유효한지 함께 확인한다.
- 이 문서에 없는 새로운 리텐션 장치(예: 이메일 알림, 캘린더 연동)를 제안받으면, 먼저 "왜 알림 인프라를 안 쓰기로 했는가"(위 핵심 전제)와 충돌하지 않는지 확인하고 OPEN_QUESTIONS.md에 올린다.

## 아직 대응하지 않은 죽는 경로 (의도적 보류)

아래는 이전 앱 실패 사례에서 나올 법하지만 이 문서의 표에는 없는 경로들이다. 의도적으로 MVP 범위 밖에 둔 것이며, 필요성이 확인되면 v2로 올린다.

- 마감일이 지나도 아무 리마인드가 없음 — 알림 인프라 없이는 구조적으로 어렵다. 공유 문구를 반복 발송하는 것이 현재의 유일한 완화책이다.
- 신규 참여자 온보딩 마찰 — 현재 설계는 고정 멤버 5~8명을 전제하므로 우선순위가 낮다.
