# VIBE_CODING.md

이 문서는 "바이브 코딩"이 실제로 무엇인지, 이 프로젝트가 어떻게 만들어졌는지를 되짚어보기 위한 기록이다. 기술적 결정 근거는 `docs/DECISIONS.md`에 이미 있으니 여기서는 **과정 자체**(무엇을 어떤 순서로, 어떻게 시켰고 AI가 어떻게 반응했는지)에 집중한다.

## 바이브 코딩이란

"바이브 코딩(vibe coding)"은 코드를 한 줄씩 직접 타이핑하는 대신, 하고 싶은 것을 자연어로 설명하고 AI가 실제 코드를 작성·실행·수정하게 하면서 대화로 소프트웨어를 만들어가는 방식이다. 2025년 초 Andrej Karpathy가 이름 붙인 이후 널리 쓰이는 용어인데, 흔히 오해되는 지점이 있다 — "그냥 프롬프트만 던지고 나오는 걸 받는다"가 아니라는 것. 이 프로젝트가 실제로 보여주는 것처럼, 잘 되는 바이브 코딩은 아래 세 가지가 같이 간다:

1. **의도를 먼저 문서로 고정한다** — 즉흥적으로 "이거 만들어줘"만 반복하지 않고, 무엇을 왜 만드는지 먼저 글로 정리한다.
2. **AI가 실제로 실행하고 검증한다** — 코드만 생성하는 게 아니라 빌드하고, 브라우저로 클릭해보고, DB를 직접 조회해서 결과를 확인한다.
3. **판단의 이유를 남긴다** — AI가 스펙에 없는 부분을 임의로 정할 때마다 "왜 이렇게 정했는지"를 기록해서, 나중에 사람이 그 판단을 검토·번복할 수 있게 한다.

## 이 프로젝트에서 실제로 있었던 일

### Phase 0 — 코드 없이 기획부터

가장 먼저 한 일은 코드를 짜는 게 아니라 `독서토론앱.md`(전체 계획서)와 `CLAUDE.md`(작업 규칙), 그리고 `docs/` 아래 스펙 문서 6개(SPEC, SCHEMA, SECURITY, DECISIONS, RETENTION, OPEN_QUESTIONS)를 만드는 것이었다. 이 단계에서 나온 게 각 Phase(1~5)별로 "이번 턴 목표 / 작업 / 하지 말 것 / 끝나면"이 적힌 프롬프트 블록이다 — 이후 대화들은 사실상 이 블록을 하나씩 실행시킨 것에 가깝다. 즉흥적으로 기능을 던지지 않고, 처음부터 "이 앱이 왜 필요한가"(구글 문서를 대체)와 "이전 시도가 왜 실패했는가"(RETENTION.md — 관리자 세팅 피로, 아카이브 부재, 로그인 번거로움)를 문서로 박아둔 게 이후 모든 판단의 기준이 됐다.

### Phase 1 — 스캐폴딩 + 스키마 + 시드

Next.js 프로젝트를 만들고, Supabase 스키마(9개 테이블)를 설계하고, 실제로 시드 데이터를 넣었다. 여기서부터 이미 "코드만 짜고 끝"이 아니었다 — Supabase MCP 도구로 실제 프로젝트를 만들고, 마이그레이션을 적용하고, `/debug` 페이지로 중첩 쿼리(발췌 답변 안에 사유더하기가 들어있는 구조)가 실제로 맞게 나오는지 직접 확인했다.

첫 배포 시도에서 `/debug` 페이지가 빌드 시점에 정적 페이지로 프리렌더되려다 실패하는 걸 실제로 겪고서야 `force-dynamic` 지정이 필요하다는 걸 알았다 — 이런 건 코드만 읽어서는 안 보이고 **실제로 빌드해봐야** 드러나는 종류의 문제다.

### Phase 2 — 인증

여기서부터 규모가 커져 코드를 쓰기 전에 "계획 모드(Plan Mode)"로 먼저 설계를 텍스트로 정리하고 승인을 받는 절차가 들어갔다. 스펙 문서에 "공통 암호 → 이름 선택 2단계"라고만 적혀 있고 그 사이를 어떻게 안전하게 이어붙일지는 안 적혀 있었는데, 이 빈틈을 그냥 넘어가지 않고 `preauth` 쿠키라는 메커니즘을 새로 설계해서 메꿨다(그리고 왜 그렇게 했는지 DECISIONS.md에 남겼다).

실제로 브라우저에서 로그인을 시도하다가 **정확한 비밀번호를 넣었는데도 로그인이 안 되는** 버그를 만났다. 원인을 추적해보니 Next.js가 `.env` 파일의 `$2b$12$...`(bcrypt 해시) 문자열을 셸 변수 치환처럼 오인식해서 조용히 깨뜨리고 있었다 — 에러 메시지 하나 없이. 이런 건 "그럴듯해 보이는 코드"만으로는 절대 못 잡고, 실제로 로그인을 시도해봐야만 나온다.

### Phase 3 — 관리자 + 템플릿 + 이관

회차 템플릿 기능은 애초 기획 문서(C절 데이터 모델)에 스키마가 통째로 빠져 있었다 — 기능만 나중에 추가됐지 테이블 설계가 안 돼 있던 것. 이걸 발견하고 이번에 새로 스키마를 설계했다.

붙여넣기 파서(구글 문서 텍스트를 논제/답변/사유더하기로 자동 변환)를 만들면서, 실제 참고할 샘플 문서가 없어서 직접 가짜 텍스트를 만들어 `npx tsx`로 파서 함수만 따로 실행시켜 검증했다. 이 과정에서 "논제 제목 줄 자체에 '발췌'라는 단어가 들어가는 경우"를 놓치는 버그를 발견해서 고쳤다.

### Phase 4 — 참여자 화면 (가장 큰 Phase)

회차 목록, 논제별/사람별/한눈에 3가지 뷰, 발췌+사유더하기 스레드, 공유 문구, 인라인 편집까지 — 이 앱의 존재 이유인 화면들을 만들었다. 여기서 바이브 코딩의 검증 루프가 가장 잘 드러난다: **두 개의 브라우저 탭을 열어 실제로 서로 다른 사람으로 로그인**하고, 한 사람이 발췌를 올리면 다른 사람이 사유를 더하는 걸 실제로 해보면서 세 가지 뷰 모두에서 정확히 반영되는지 확인했다. 코드 리뷰만으로는 "될 것 같다"였겠지만, 실제로 해보고서야 "된다"로 확정됐다.

이 Phase에서 Supabase 타입 정의에 관계(FK) 메타데이터가 빠져 있어서 중첩 조회(`book:books(title)` 같은 조인)가 타입 체크에서 전부 `never`로 깨지는 문제, Server Component에서 만든 함수를 Client Component에 직접 넘기다 런타임 에러가 나는 문제 등도 실제로 빌드하고 실행해보다가 발견해서 고쳤다.

### Phase 5 — 배포

keep-alive cron, Vercel 환경변수, 자체 보안 점검(RLS 켜짐 확인, 시크릿 노출 여부 grep, 모든 서버 액션에 권한 검사가 있는지 파일 하나하나 확인)까지 진행했다. 환경변수를 Vercel에 옮기는 과정에서 이스케이프 처리가 잘못돼 로그인 해시가 깨진 걸 등록 직후 실제로 로그인해보고서야 발견해서 바로 고쳤다 — "등록했다"와 "실제로 동작한다"는 다르다는 걸 보여주는 사례다.

## 정리: 이 프로젝트가 보여주는 바이브 코딩의 실제 모습

- **문서가 먼저, 코드는 그다음.** 스펙과 이유를 먼저 글로 남기면, AI가 스펙에 없는 부분을 만날 때마다 "이렇게 정하고 왜 그런지 기록한다"는 일관된 패턴이 생긴다.
- **"만들었다"와 "된다"는 다르다.** 이 프로젝트에서 실제로 잡힌 버그 대부분은 코드 리뷰가 아니라 빌드·로그인·브라우저 클릭·DB 조회처럼 **실제로 실행**해봐야 드러나는 것들이었다.
- **큰 작업 전에는 계획을 먼저 보여주고 승인받는다.** 특히 여러 파일에 걸치거나 스펙에 없는 설계 판단이 필요한 작업(인증 방식, 템플릿 스키마, 파서 규칙)은 실행 전에 먼저 설계를 정리해서 확인받았다.
- **AI가 인프라도 직접 조작할 수 있다.** git/GitHub, Supabase(마이그레이션·시드·SQL 조회), Vercel(환경변수·배포)까지 전부 자연어 대화로 진행됐다 — 코드 저장소 밖의 작업도 바이브 코딩의 영역이다.
- **사람의 역할은 "타이핑"에서 "판단·승인·방향 제시"로 옮겨간다.** 이 대화 전체에서 실제 코드를 한 줄도 직접 치지 않았지만, Phase 순서를 정하고, 계획을 승인하고, 애매한 지점에서 선택지를 골라준 건 전부 사람이었다.
