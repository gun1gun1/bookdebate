# DECISIONS.md

주요 설계 결정과 그 이유, 그리고 채택하지 않은 대안. Phase가 진행되며 실제로 바뀐 결정은 이 문서 하단 "Phase 진행 중 변경 이력"에 계속 추가한다.

## 인증: 공통 암호 + 이름 선택 (Supabase Auth 미사용)

**결정**: 이메일/비밀번호나 OAuth 없이, 공통 암호로 외부인을 차단하고 명단에서 이름을 선택해 신원을 지정한다. Supabase Auth는 쓰지 않는다.

**이유**: 참여자가 5~8명의 고정 멤버이고 이미 서로 누구인지 안다. 이메일 인증, 비밀번호 재설정 같은 계정 관리 오버헤드는 이 규모에서 실질적 이득이 없다. 대신 "외부인 차단"과 "내부에서 누가 썼는지 구분"이라는 두 가지 실제 필요만 충족하면 된다.

**대안과 미채택 이유**:
- Supabase Auth(이메일/매직링크) — 계정 복구, 이메일 전달률 등 이 규모에 안 맞는 복잡도를 들여온다. 또한 Supabase Auth를 쓰면 `auth.uid()` 기반 RLS를 쓰게 될 유인이 생기는데, 이는 아래 "RLS 전면 거부" 결정과 충돌한다.
- 참여자별 개별 계정(자체 구현) — 개인 PIN을 스위치(`REQUIRE_MEMBER_PIN`)로 준비해뒀으므로, 필요해지면 코드 변경 없이 켤 수 있다. 지금 강제하지 않는 이유는 "로그인이 매번 귀찮음"이 이전 앱이 죽은 원인 중 하나였기 때문(RETENTION.md 참고).

## RLS 전면 거부 + service-role 서버 전용 접근

**결정**: 전 테이블 RLS를 켜고 정책은 만들지 않는다(익명 키로는 아무것도 못 함). 모든 DB 접근은 Next.js 서버가 service-role 키로 수행한다.

**이유**: Supabase Auth를 쓰지 않기로 한 순간 `auth.uid()`가 없으므로 세밀한 RLS 정책을 짤 방법이 없다. 정책을 억지로 만들면 커스텀 클레임을 흉내 내는 우회 장치가 필요해지고, 그 장치 자체가 새로운 공격 표면이 된다. 차라리 DB 레벨은 "전면 거부"로 단순하게 두고, 권한 판단을 애플리케이션(서버) 레벨 한 곳에 모으는 편이 감사하기 쉽다.

**대안과 미채택 이유**:
- Supabase Auth + `auth.uid()` 기반 RLS 정책 — 이 프로젝트 규모에 비해 정책 설계·테스트 비용이 크고, "인증 방식 자체를 안 쓰기로" 한 위 결정과 모순된다.
- anon 키를 클라이언트에 노출하고 세밀한 RLS로 방어 — Postgres RLS 정책 실수는 발견이 늦고(조용히 더 열려 있음) 피해가 크다. 서버 전용 접근은 실수해도 "전부 막힘" 방향으로 fail-safe하다.

## URL을 `/s/[id]`로 짧게

**결정**: 회차 상세 경로를 `/sessions/[id]`가 아니라 `/s/[id]`로 둔다.

**이유**: 공유 문구(RETENTION.md)에 절대 URL이 그대로 단톡방에 붙여넣어진다. 짧은 URL이 메시지 안에서 더 잘 보이고 덜 잘린다.

## 리치 에디터 대신 `textarea` + `whitespace-pre-wrap`

**결정**: 답변/사유더하기 입력에 WYSIWYG나 마크다운 에디터를 쓰지 않는다. 단, 발췌문(`excerpt_text`)만 별도 필드로 분리한다.

**이유**: 참여자가 40~50대이고 월 1회만 쓴다 — 에디터 사용법을 매번 재학습하게 만드는 것보다 익숙한 텍스트 입력이 낫다. 리치 에디터는 저장 포맷(HTML/마크다운) 선택, XSS 방어, 마이그레이션 부담 등 이 앱의 실제 필요에 비해 큰 복잡도를 들여온다. 발췌문만 분리한 이유는 렌더링 시 시각적으로(세리프+인용 서식) 구분해야 하기 때문이지, 서식 기능이 필요해서가 아니다.

## 자동 저장 없음, 명시적 저장 버튼

**결정**: 입력 중 자동 저장하지 않는다. 저장 버튼을 명시하고, 저장 후 "저장됨 · 방금"을 3초 표시하며, 이탈 시 확인창을 띄운다.

**이유**: 자동 저장은 "저장되고 있는지 불확실한 느낌"을 만들 수 있고, 특히 이 앱처럼 한 번 쓰고 오래 안 돌아오는 사용 패턴에서는 사용자가 저장 여부를 스스로 확신할 수 있는 것이 중요하다. 명시적 확인이 신뢰를 준다.

## 세션 유효기간 90일

**결정**: JWT 세션 쿠키의 `maxAge`를 90일로 둔다(일반적인 웹앱보다 김).

**이유**: 사용 빈도가 월 1회다. 30일로 두면 매달 재로그인하게 되는데, "로그인이 매번 귀찮음"이 이전 앱이 죽은 경로 중 하나로 지목되었다(RETENTION.md). 참여자 규모가 작고 서로 신원이 확실하므로 긴 세션의 위험보다 재로그인 마찰의 비용이 크다고 판단했다.

## 데스크톱 우선, 매트릭스 뷰는 데스크톱 전용

**결정**: 데스크톱을 주 환경으로 설계하고, "한눈에(매트릭스)" 뷰는 1024px 미만에서 아예 숨긴다.

**이유**: v1 설계 이후 실제 사용 맥락을 다시 보니 참여자들이 토론 직전 앉은 자리에서 노트북으로 전체 판을 훑어보는 경우가 많다는 관찰이 있었다(v1→v2 변경 사유 중 "데스크톱 우선으로 전환"). 좁은 화면에 매트릭스를 욱여넣는 것보다, 그 뷰 자체를 데스크톱 전용 기능으로 명확히 규정하는 편이 낫다고 판단했다.

## 다크 모드 없음

**결정**: 다크 모드를 만들지 않는다.

**이유**: 긴 글을 오래 읽는 화면이라는 판단 아래 본문 배경은 밝게 유지하기로 했고(디자인 지침), 다크 모드까지 지원하면 유지보수 대상(색상 토큰 이중화)이 늘어나는 데 비해 이 사용자층·사용 빈도에서 얻는 이득이 작다고 봤다.

## 회차 템플릿 + 이전 회차 복제 기능

**결정**: 논제 묶음을 템플릿으로 저장하고, 새 회차 생성 시 템플릿에서 시작하거나 이전 회차 구조를 복제할 수 있게 한다.

**이유**: 원본 문서 구조를 보면 논제 1번(요약+별점)과 2번(발췌 나눔)이 매달 사실상 고정 패턴이다. 이 반복 세팅 노동을 줄이지 않으면 관리자가 지치고, 관리자가 지치면 앱이 죽는다(RETENTION.md의 핵심 가설).

## MVP는 화면만 줄이고 스키마는 v2까지 미리 반영

**결정**: `choice` 논제, `votes`, `blind_enabled` 등 v2 기능의 스키마를 Phase 1부터 만들어 두되, 화면(UI)은 MVP에서 구현하지 않는다.

**이유**: 나중에 v2 기능을 켤 때 마이그레이션으로 인한 다운타임이나 기존 데이터 백필 문제를 피하기 위함이다. 스키마 변경은 화면 추가보다 되돌리기 어렵고 위험이 크므로, 위험이 적은 지금 미리 반영해 둔다.

## 관리자도 타인 명의로 답변을 대리 작성하지 않는다

**결정**: SECURITY.md 권한 매트릭스에서 관리자조차 "타인 answer 작성/수정"은 불가로 명시한다.

**이유**: 이 앱의 데이터는 "누가 실제로 그렇게 답했는가"가 핵심 가치다(토론 기록 아카이브). 관리자 편의를 위해 대리 작성을 허용하면 그 기록의 신뢰성이 깨진다. 관리자가 할 수 있는 것은 구조(논제·회차·멤버) 관리이지 내용 대필이 아니다.

## 삭제 대신 비활성화(soft delete) — `members.is_active`

**결정**: 참여자를 명단에서 제거할 때 행을 삭제하지 않고 `is_active = false`로 둔다.

**이유**: 과거 회차의 `answers`/`replies`가 그 멤버를 참조하고 있으므로, 하드 삭제하면 아카이브가 깨지거나(FK 위반) 고아 데이터가 남는다. "지난 회차와 지난 책을 다시 찾을 수 없다"는 이전 앱의 실패 경로(RETENTION.md)를 반복하지 않기 위해 아카이브 무결성을 우선한다.

## 붙여넣기 이관은 항상 미리보기 → 명시적 확인 2단계

**결정**: 파싱 결과를 즉시 저장하지 않고 반드시 미리보기(생성될 논제/답변/사유더하기 개수 요약)를 먼저 보여준 뒤 확인을 받는다.

**이유**: 정규식/휴리스틱 기반 파서(SPEC.md, SECURITY.md 참고)는 원본 문서의 표기 변형(예: 이름 축약, 번호 표기 차이)에 취약할 수 있다. 되돌리기 어려운 대량 쓰기 전에 사람이 결과를 확인할 기회를 두는 것이 파서 정확도를 높이는 것보다 비용 대비 효과가 크다.

## Phase 0 후속 결정 — OPEN_QUESTIONS.md 1~6번 답변 (2026-08-16)

Phase 1 착수 전 정해야 했던 데이터/정책 질문 6개에 사용자가 직접 답했다. 각 결정과 그에 따른 후속 조치는 아래와 같다.

### 본인 answer 삭제: 허용, 하위 replies도 함께 삭제

**결정**: 참여자가 본인이 쓴 answer(소감/발췌)를 삭제할 수 있다. 삭제 시 그 answer에 달린 모든 `replies`(사유 더하기)도 함께 삭제된다.

**이유**: 삭제를 완전히 막는 것보다 사용자에게 더 직관적인 동작이다. 다만 다른 참여자가 이미 사유를 덧붙인 스레드가 통째로 사라질 수 있으므로, 삭제 전 "사유더하기 N개도 함께 삭제됩니다" 경고를 반드시 보여줘야 한다(SPEC.md에 반영).

**후속 조치**: `replies.answer_id` FK에 `ON DELETE CASCADE`를 건다(SCHEMA.md). Server Action에서 삭제 확인 모달에 하위 reply 개수를 표시한다(SPEC.md).

### `members.aliases` 겹침: 검증하지 않음

**결정**: 별칭이 다른 멤버의 이름/별칭과 겹치는지 저장 시점에 검증하지 않는다.

**이유**: 참여자가 5~8명으로 고정되어 있고 관리자가 직접 입력하므로, 실제 겹침 발생 확률이 낮고 검증 로직(DB 제약이든 애플리케이션 검증이든)을 추가하는 비용이 실익보다 크다고 판단했다. 겹침이 실제로 발생하면(붙여넣기 파서나 로그인 이름 매칭에서 모호함 유발) 관리자가 화면에서 직접 발견하고 고치는 것으로 충분하다.

**후속 조치**: 없음(의도적으로 미구현). 나중에 문제가 실제로 발생하면 재검토한다.

### `kind != 'excerpt'` topic의 answer에는 reply 금지 (Server Action 레벨)

**결정**: `replies` 생성은 대상 `answer`가 속한 `topic.kind === 'excerpt'`일 때만 Server Action이 허용한다. DB 트리거는 두지 않는다.

**이유**: DB 트리거보다 Server Action에서의 검증이 유지보수 관점에서 더 명시적이고 Codex/Gemini CLI로도 읽기 쉽다(AGENTS.md의 "마법 같은 추상화 회피" 원칙과 일치). 이 앱의 쓰기 경로가 전부 Server Action을 통하기로 되어 있으므로(SECURITY.md) 트리거로 이중 방어할 필요성이 낮다.

**후속 조치**: reply 생성 Server Action 첫 부분에서 `answer → topic` 조인 조회 후 `kind` 확인, 아니면 거부. SECURITY.md 서버 측 필수 검증 체크리스트에 항목 추가.

### 본인 발췌에 본인이 reply: 허용

**결정**: 참여자가 본인이 올린 excerpt answer에 스스로 사유 더하기를 다는 것을 허용한다.

**이유**: 나중에 스스로 보충 설명을 덧붙이고 싶은 자연스러운 사용 사례이며, 막을 이유(스팸, 오남용 등)가 이 규모의 사적 모임에는 해당하지 않는다.

**후속 조치**: 없음(제약 추가하지 않음 — `replies.member_id === answer.member_id`인 경우도 정상 허용).

### `closed` 이후 새 답변/사유더하기 작성: 완전히 막음

**결정**: 회차 상태가 `closed`가 되면 새로운 answer/reply 작성과 기존 것의 수정을 서버에서 거부한다. 다시 쓰려면 관리자가 상태를 `open`으로 되돌려야 한다.

**이유**: "마감"의 의미를 명확하게 유지하는 편이 참여자에게 예측 가능하다. 늦참자 구제가 필요하면 관리자가 명시적으로 재오픈하는 것이 암묵적으로 계속 열어두는 것보다 안전하다(재오픈 자체가 이미 있는 `status` 필드로 처리되므로 새 메커니즘이 필요 없다).

**후속 조치**: 아래 "draft 노출" 결정과 통합해 하나의 규칙으로 구현한다.

### `draft` 상태 회차: 논제까지 보이되 작성만 막음

**결정**: `draft` 상태에서도 참여자는 논제 목록과 내용을 볼 수 있다. 다만 답변/사유더하기 작성은 막는다.

**이유**: 완전히 숨기면 참여자가 다가올 논제를 미리 읽고 생각을 정리할 시간을 뺏는다. 반대로 작성까지 허용하면 관리자가 아직 다듬는 중인 논제 구성에 답변이 달려버리는 문제가 생긴다.

**후속 조치**: 위 `closed` 결정과 합쳐 **쓰기 권한의 단일 규칙**으로 구현한다 — *답변/사유더하기 생성·수정·삭제는 `session.status === 'open'`일 때만 허용*. `draft`와 `closed` 둘 다 이 하나의 조건으로 자동으로 막히므로, 상태별로 분기 로직을 따로 두지 않는다. SECURITY.md 서버 측 필수 검증 체크리스트와 SPEC.md 상태 전이 절에 반영.

### Phase 1: `/_debug` → `/debug` (2026-08-16)

**결정**: 계획서(`독서토론앱.md`)의 `app/_debug/page.tsx`를 `app/debug/page.tsx`로 옮기고, 라우트를 `/_debug`가 아니라 `/debug`로 둔다.

**이유**: Next.js App Router는 언더스코어로 시작하는 폴더(`_folder`)를 "private folder"로 취급해 라우팅에서 완전히 제외한다(`node_modules/next/dist/docs/01-app/01-getting-started/02-project-structure.md`의 "Route groups and private folders" 절에서 확인). 즉 `app/_debug/page.tsx`는 애초에 `/_debug` 경로를 만들지 않는다 — 계획 수립 시점에는 반영되지 않았던 프레임워크 제약이다. 폴더명만 다르고 목적·수명(Phase 4에서 삭제)은 계획과 동일하다.

**영향받는 문서**: `독서토론앱.md`의 Phase 1/4 본문과 체크포인트 표는 `/_debug`로 적혀 있으나 실제 경로는 `/debug`로 읽는다. 이 파일 외 별도 수정은 하지 않았다(계획서 원문은 그대로 두고 이 결정 기록으로 정정한다).
